# 让控制器自己守住朝向：航向保持进闭环

- 日期：2026-11-02
- 分支：`task/heading-hold-rust`
- 结论：走路命令现在可以带一个 `heading` 块，控制器在每一步推理前**把修正加到**操作者命令的 `awz` 上，写进策略看得到的通道。仿真里横向误差从 1.84 m / 19.6° 降到 0.10 m / 0.7°（铺地 10 m，四条策略 × 5 个种子，中位数；增益扫描见 §五），代价是零训练；`cargo test` 218 项、`pytest` 1681 项全过。

## 一、问题

策略只被要求跟上速度，没有被告知往哪个方向走。直走 10 m 的实测：铺地上四条策略偏 0.6–1.8 m、5–20°，50 mm 起伏上偏到 ±9 m、±93°（`docs/reports/research-heading-drift-20261102.md`）。训练里 `twist` 没有航向通道（`ranges.heading = None`、`rel_heading_envs = 0`），控制器里也没有任何东西在读 `imu.quat`。所以这是"按现状不能上机器人"的缺陷，不是精度问题。

## 二、做法的选择

修正有两种放法：训练一个会看航向的策略，或者在控制器里闭环。选了后者，理由是零训练、无仿真到真机的模型差距、且不改变策略本身——另一个理由更实际：它修的是下一次训练结果的评判口径，如果先训练再补闭环，那批数字要重测。

闭环的输入必须是策略本来就看得到的量，否则等于给策略喂分布外的观测。所以修正写进 `ang_vel_z`：这一通道在观测里已有，训练时它的范围是 ±0.75 rad/s。

## 三、改了什么

| 层 | 文件 | 内容 |
|---|---|---|
| 控制律 | `deploy/fsm/src/heading.rs`（新） | `HeadingHold`：命令速度高于 0.02 m/s 时启动，第一步记下航向，之后每步 `wrap(锚点 − 当前航向)`，按 `kp` 成比例、限幅 `max_rate`、留 `deadband`；期望转向时锚点按**请求**推进，修正取 `awz + 修正` 再夹到契约的 `|ang_vel_z|` 上沿 |
| 接入 | `deploy/fsm/src/control.rs` | 每条模式在构造时从契约的控制器块建一个 hold，`tick` 里在整型（`CommandShaper`）之后、观测组装之前写入 `yaw_rate`；策略接管时清零 |
| 契约 | `tasks/jumper/common/mdp/controls.py` | `Command.heading`，校验后才认：`kp` 必填且为正，`max_rate`、`deadband` 不为负，写了不认识的键直接拒绝 |
| 说明书 | `tasks/jumper/{flat,tripod,ripple,tetrapod,posture}/controls.yaml` | 走路命令带 `heading: { kp: 1.0, max_rate: 0.5 }`，四个运动任务保持逐字一致 |
| 文档 | `deploy/BUNDLE.md` | `heading` 块的三个数、参考系、"带 hook 的模式拒绝应用"这条边界 |

两处是**拒绝**而不是悄悄不生效，因为悄悄丢掉的保持和生效的保持长得一样：字段不合法（`max_rate` 超过 `|ang_vel_z|` 上沿、`deadband` 到 π、写了不认识的键），以及在一个带 hook 的模式上要求保持（`jumper.five_foot` 的 hook 会取反 `awz`，合上去会朝反方向修）。后者在构造时抛 `Error::Inconsistent`，说明该模式要用的是一份不带这个块的契约。

前馈这条是 review 抓出来的，不是我想出来的：最初把 `kp·误差` 直接赋给 `yaw_rate`，等于抹掉操作者的转向请求——持续的 0.5 rad/s 会滞后 `awz/kp` = 0.5 rad ≈ 29°，环在跟操作者对抗。

第二轮 review 又抓到四处真问题，值得记下来因为它们都是"看起来对"的写法：

- **带子取成了幅值**。原来用 `max(|lo|,|hi|)` 做对称夹取；训练范围不对称时（`[-0.3, 0.9]`），请求 −0.3 加修正 −0.5 得到 −0.8，0.9 那头上沿根本不拦它——策略拿到了自己下限之外的速率。现在带原样传 `[lo, hi]`。
- **`heading: null` 与没写等价**。serde 的 `Option` 把显式 null 读成"没有这个键"，而导出侧拒绝半写的块：同一份内容在 yaml 里不合法、在 bundle 里合法。现在用自定义 deserializer，null 报错。
- **非有限数只有一边拦**。Python 用 `value > low` 判断，`inf` 过关，导出成 `Infinity`（不是 JSON），到机器上是一次语法错误而不是一句指名道姓的拒绝。Python 侧补 `math.isfinite`。
- **两条命令各带一块**。Rust 侧报的是"轴被两条命令共用"（症状），不是"两块航向"（原因）；Python 侧完全不拦。两边都改：计数在轴检查之前，导出时也拒绝。

还有一处是文档说的和代码做的不一致：`of()` 的注释写"这里不可能查不到"，代码却静默用 `max_rate` 兜底；改成 `expect`，因为兜底会让跳过 `check` 的调用方重新拿到带外速率。

## 四、验证

- `cargo test`：**215 项通过**（新增 20 项：15 项在 `heading.rs`，4 项在 `control.rs`，1 项在 `operator.rs`）。
- `pytest`：1680 通过、2 跳过；`ruff check tasks tests deploy` 全过。
- 变异检查（每个都还原）：误差符号取反、去掉 `|ang_vel_z|` 夹取、站立时不清锚点、去掉锚点推进、不跟随体扭、去掉前馈（`awz + 修正` 改成只给修正）—— 全部被抓；`control.rs` 里"契约要了航向就修正、没要就一个字不动"两侧都验。
- 夹取那条最初**没被抓**：我给它的用例误差方向让和恰好没越过上沿。补了一侧（请求 +0.7、误差 +0.5，和 1.2 对 0.75 上沿）之后才死。记在这里，因为"测试通过"和"测试在位"是两件事。
- 第二轮之后补的变异：对称夹取（死：非对称带用例报 −0.8）、去掉 NaN 守卫（死：NaN 用例）、去掉 null 反序列化（死：null 用例被接受）、把两块计数挪回轴检查之后（死：诊断变成轴重复）、Python 侧去掉有限数校验/双击校验/轴上限校验（各自死在对应用例）。
- 唯一没被抓的变异是"锚点推进后不再 wrap"：它等价，因为后面 `wrap(锚点 − 航向)` 会把 2π 抹掉。记在这里，免得下次当成测试漏洞。
- 契约侧变异：不导出 `heading` 块、把未知键放过、把缺失的 `kp` 默认为 1 —— 都被 `tests/test_controls.py` 抓。
- 第三轮之后补的变异：Rust 侧去掉零穿越规则（死：单侧带用例）、NaN 时重新锚定（死：NaN 用例报 `the anchor was re-adopted`）、两块报错不点名（死：契约用例读不到 `'twist'` 与 `'extra'`）、去掉构造期带校验（死：`should_panic` 用例）、Python 侧去掉零穿越规则与"没有命令项"的拒绝（各自死在对应用例）。
- 第四轮之后补的变异：去掉构造期跨零断言（死：单侧带用例）、NaN 拍不推进锚点（死：`a_skipped_tick_still_records_the_commanded_turn`）、Python 去掉有限性校验（死：`(-inf, inf)` 用例）。
- 第四轮还指出两处"两边拒绝的集合不等"：Python 放过 `(-inf, inf)`，而控制器拒它；以及测试的匹配片段和"缺 rest"的报错重叠，会在 tripod 将来给轴加 rest 时悄悄测错规则。两处都按同集合同步了。
- 第五轮五条都落在前一轮修复的边缘，全部接受：`math.isfinite` 只挡住 Python 的无穷，契约按 `[f32; 2]` 读回，`1e39` 在这里有限、在机器人上却是 `inf`，于是改按 f32 上界判；`wrap` 把非有限角映射成 0，所以一个 NaN 的 `yaw_rate` 不是"这一拍不推进"，而是把参考瞬移到 0 rad，控制器随后以 `max_rate` 开过去——非数请求现在按"没有请求"处理；构造期断言补上 `kp`、`max_rate`、`dt`，非有限 `kp` 会让 NaN 直接进策略。
- 零穿越规则第一版写成 `lo <= 0 <= hi`，于是 `[0.0, 0.5]` 通过——但它正是要拒绝的那个：`clamp(rate, 0.0, 0.5)` 把负修正全变成零。改成两侧都留余地后用例才红，记在这里：边界写成闭区间时，端点上那一格就是全部差别。
- 端到端：`control.rs` 的集成测试让一个两关节契约走起来，机器人偏左 0.2 rad 时观测里的转向通道读到 −0.2；把块拿掉，读到恰好 0。

### 增益扫描：1.0 偏低，2.0 是拐点

四档 `kp`，其余固定（`max_rate 0.5`、同一批 4 条策略 × 铺地 / 50 mm × 5 个种子），
闭环重走十米，逐格配对：

| kp | 横向残差中位数 | 航向残差 | 饱和 | 控制步数 |
|---|---|---|---|---|
| 0.5 | 0.214 m | 2.1° | 0 % | 1078 |
| 1.0 | 0.163 m | 1.4° | 0 % | 1076 |
| **2.0** | **0.096 m** | 0.7° | 0 %（50 mm 上 10 %） | 1081 |
| 4.0 | 0.097 m | 0.4° | 0 %（50 mm 上 3–12 %） | 1078 |

读法：增益翻倍把残差砍掉一半，到 2.0 之后不再降；4.0 只多买 0.3° 的航向，代价是
最多 12 % 的步数贴在 `max_rate` 上（环退化成"一直以 0.5 rad/s 抢方向"）。
所以契约里的 `kp` 从 1.0 改成 2.0——这不是调参，是 1.0 一直把一半误差留在地上。

一处要说明：`rough5-bext` 在 50 mm 上 `kp=1.0` 的 0.77 m 残差曾判为打滑、环外，
这次 `kp=2.0` 把它压到 0.102 m。打滑的那部分确实在环外，但一次打滑要靠"航向已经偏了
再修回来"来收敛，增益低时收敛得慢，量出来就像打滑本身——两个效应在同一格里，本报告
不拆分。

`kp` 是每任务的值，只扫过 tripod 自己的策略，所以只有 tripod 改成 2.0；其余四个步态
的 yaw 响应没测过，保持 1.0，这个差异写在 `tests/test_controls.py::DIVERGED` 里并附理由，
不是靠"大家都不一样"来掩盖。

## 五、边界

- 没有板子。以上全部是仿真和单元测试；机器人上的行为未实测。
- 真机侧还有一段没写：`kp` 与 `deadband` 的标定要真机才能定，现在是仿真里 `kp=2.0`、铺地上 0 % 饱和的那组（50 mm 上 10 %）。
- `max_rate` 上限取 0.5，而训练分布到 0.75；更大的修正会先把命令推到分布边缘。
- 只有 `imu.valid` 时才修正；IMU 无效时命令原样通过，不静默清零。
- 机器人没有文件可读这个块：它随策略契约下发。已实测导出侧确实带上了它——`controller_contract(...)` 产出的 twist 命令块里是 `"heading": {"kp": 1.0, "max_rate": 0.5, "deadband": 0.0}`；`deploy/manifests.json` 只管打包，不需要也不应该另写一份。
- 带 hook 的模式在构造期拒绝（见第三节），不是静默跳过。
- 修正只跟随 IMU 的 yaw；姿态那一拍非有限时跳过这一拍——保留参考、仍记下这一步请求的转向，不赌一个坏读数，也不把操作者主动的转向读成漂移。非有限的 `yaw_rate` 按「没有请求」处理（`wrap` 会把非有限角映射成 0，直接积分等于把参考瞬移到 0 rad）。
- 修正只跟随 IMU 的航向；打滑造成的横向位移在环外，不会被修回来（50 mm 起伏上纯追踪才把它压下去：`research-heading-loop-20261102.md`）。
